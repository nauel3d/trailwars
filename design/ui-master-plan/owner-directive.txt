The UI must look excellent across supported phones, tablets, desktops, laptops, ultrawide monitors, and controller-driven displays.

**Do not build one desktop layout and shrink it with UIScale.**

That is not acceptable.

The UI must intelligently rearrange itself depending on the available viewport.

## Research the best Roblox techniques

Investigate current Roblox documentation for:

- UIScale.
- UDim2 scale and offset.
- UIListLayout.
- UIFlexItem and flex-style layouts.
- UIGridLayout.
- AutomaticSize.
- AutomaticCanvasSize.
- UISizeConstraint.
- UITextSizeConstraint.
- UIAspectRatioConstraint.
- AnchorPoint.
- Safe area handling.
- ScrollingFrame.
- Nine-slice images.
- Text wrapping.
- Layout measurement.
- Input modality changes.

Use the appropriate combination rather than applying one approach everywhere.

Avoid conflicting constraints, sizing loops, or deep nested structures that are difficult to maintain.

## Adaptive layout philosophy

Create several composition modes.

### Spacious landscape

Desktop and large screens.

Allow more horizontal composition, side-by-side content, larger previews, and expanded navigation.

### Compact landscape

Small laptops and mobile devices in landscape.

Reduce decorative space, reorganize panels, preserve essential actions, and maintain readable text.

### Tablet / intermediate

Use adaptive grids, proportional content regions, and deliberate navigation placement.

### Narrow portrait

Use vertically stacked sections, compact navigation, and scrolling where necessary.

Keep important controls accessible.

Do not force a large horizontal layout into a tiny screen.

## Size changes at runtime

The UI must also handle:

- Device rotation.
- Window resizing.
- Changing input method.
- Safe-area changes.
- Text scaling.
- Long player names.
- Large currency values.
- Localization-ready text.
- Mobile notches and system bars.
- Tablet split-screen or unusual available sizes where Roblox supports them.

Layout rules should depend primarily on actual available content dimensions, not just the device name.

# 9. ABANDON DEAD ENDS — VERY IMPORTANT

You have explicit permission to rethink and replace a technical approach when it is not working.

I do not want you endlessly debugging something that should have been replaced.

Examples:

If nine-slice rendering cannot preserve a particular shape or bevel, investigate alternative asset construction.

If a design importer generates unusable hierarchies, stop relying on it.

If manually reconstructing artwork is too slow, investigate another method.

If a component architecture becomes excessively complicated, simplify or replace it.

If an animation technique has unacceptable frame-time costs, remove or redesign it.

If a font cannot achieve the desired appearance or readability, find a better supported alternative.

If an approach works on desktop but fails badly on phones, reconsider the architecture instead of adding endless device-specific patches.

## Pivot procedure

When a significant approach repeatedly fails:

1. Identify the actual problem.
2. Gather evidence.
3. Explain why the current technique is unsuitable.
4. Research at least two plausible alternatives when practical.
5. Test the most promising alternative in a small isolated example.
6. Compare quality, performance, complexity, and maintenance.
7. Choose the strongest approach.
8. Preserve useful working code.
9. Continue.

Timebox experimentation.

After roughly two meaningful failed attempts at the same technique, reassess rather than blindly trying more variations.

Do not become attached to a solution simply because you've already spent time on it.

**The objective is the best result, not defending the first implementation.**

Do not silently abandon the approved visual identity. Technical solutions may change; major aesthetic changes still require my approval.
